# Robin Hood session applet

**Native sign-in, secure credential persistence and OAuth renewal are integrated.** Add Account and Reauthenticate open a native form for email/password, optional authenticator code, mobile approval and supported SMS/email verification. The header-aligned standalone flow acquired a complete grant in a user-operated desktop test; production integration is verified offline with loopback transports and injected stores, not a live production login or trade. This is an unofficial compatibility flow, not a provider-supported API or MFA bypass.

**The Android Robin Hood launcher remains disabled.** The native code can be cross-compiled, but Android device authentication/runtime acceptance has not been verified and platform enablement is outside this change. Retained browser compatibility scaffolding is not the production authentication route.

`config/robinhood-api.json` contains the endpoint URLs, HTTP verbs, body encodings, and raw request headers observed in `jmfernandes/robin_stocks` at commit `1b4ef98` (2026-02-10). This is an **unofficial source map**, not confirmation that the service still accepts those requests. The typed `TokenRefresh` implementation is an additional, separately verified contract from OAuth RFC6749 section6 and the official public web client (module468781, `postTokenRefreshRequest`); it is not claimed to be automatic behavior of that upstream snapshot. No invented `Device-Hardware-ID` header is used.

`RHNetworkEngine` loads base endpoint URLs from configuration; the typed stock transport additionally enforces a compiled-in provider origin/path allowlist. Its platform-specific User-Agent overrides any configured value. Configured `Accept-Encoding` is ignored so Qt negotiates supported encodings and automatically decompresses responses before JSON parsing. The applet loads the packaged `:/robinhood/config/robinhood-api.json` at runtime; offline tests can load a loopback JSON file instead. `send(endpointKey, values, query, body, &error)` returns a `QNetworkReply *` on success, or null and a non-secret error string if dispatch was rejected; the caller handles completion and calls `deleteLater()` on the reply. Loading configuration sends nothing. `BodyDefaults` provides non-secret, endpoint-specific form or JSON fields that callers can override.

`values` supplies URL placeholders (percent-encoded as path/query components) and header placeholders (such as `token_type` and `access_token`). `query` adds query parameters; `body` is a `QVariantMap` encoded according to the endpoint's `BodyEncoding`: `form`, `json`, or `none`. Form booleans use Python Requests-compatible `True`/`False`; null form values are omitted. No credentials or tokens belong in this JSON file. Only HTTPS endpoints and loopback HTTP for offline tests are accepted, and redirects are not followed automatically.

`RobinHoodApplet` injects `RHNativeAuthClient` into `RHSessionManager`; production exposes no `RobinBrowser` context and instantiates no WebView. Historical browser runtime entry points are retained as no-ops. The native client preserves the reviewed upstream request headers and bounded verification workflow; TLS validation stays enabled, redirects are rejected, and unsupported/denied verification fails closed. Native `nativeLoginWorking` distinguishes actual network work from the manager-wide admission reservation, allowing credential/code entry while unrelated session operations remain blocked. Auto Mode remains unavailable; Publics and stock-order build policy are unchanged.

The compatibility-only `RHBrowserLogin` observes `__Host-Web-App-Secondary-Access-Token` through a C++ callback. Primary detection from native Authorization headers is disabled: a refreshed secondary bearer can precede its cookie notification, so difference from the last observed cookie cannot establish token class. No primary interceptor is installed. The compatibility-only primary handler is never invoked; consumers configuring it retain a bounded secondary fallback, not provenance evidence. Production installs no browser handler; historical browser tests install only the secondary handler. Tokens never enter JavaScript or token-valued QML signals/properties. Desktop uses a fresh off-the-record WebEngineProfile and native QWebEngineCookieStore; The disabled Android scaffolding uses QtWebView and native CookieManager.getCookie for the fixed official URL on the Android UI thread. Generation checks, trusted HTTPS navigation, exact cookie name/root host/path and secure-cookie policy reject stale or unsafe captures. Android clears only the named secondary cookie before loading the site, not unrelated application cookies.

The separate `RHAccountModel` contains one read-only item per verified brokerage account. Structured `brokerage_account_type` takes precedence over cash/margin mechanics: individual is **Standard Brokerage**, ira_traditional is **IRA**, and ira_roth is **Roth IRA**. Known legacy structured aliases are supported; ambiguous or unsupported products show **Account type unavailable**, not a guessed IRA subtype. Nicknames/descriptions do not determine classification. Roles include `displayName`, `accountNumber`, formatted `currentBalance`, `holdings`, `holdingsUpdatedAt`, `holdingsStatus`, and `holdingsError`. Balances prefer `total_equity`/`equity`, then cash for non-margin accounts; missing/invalid values remain Unavailable, never fabricated zeroes. Phoenix/live streaming balances are not enabled.

`RHSessionManager` accepts native grants only through a C++ callback, then verifies the complete grant/scope, UserProfile email and stable principal, and Accounts before writing any email/password credentials. Reauthentication must match the selected saved principal. Failed/rejected/cancelled/mismatched attempts do not replace the saved record. Username/password staging is encrypted in RAM, with short-lived dispatch copies; passwords, tokens and verification codes are not QML getters/model roles or log fields. The UI masks and clears sensitive entry fields after accepted submission and when hidden/cancelled/saved/destroyed.

One strict version-2 OAuth envelope stores the full original provider response and original binding together with separately namespaced verified email/password in the existing OS-backed QtKeychain slot (`PublicsTradingInterface.RobinHood`, `RobinHoodAuthX`, insecure fallback disabled). New native profile names in `robinhood/sessions.json` are opaque placeholders, not plaintext emails; verified email display names hydrate asynchronously from secure records using principal/revision/digest/operation checks. Cache updates and renewal keep disk labels opaque. Bare bearer and version-1 grant records remain readable; successful native reauthentication migrates the selected entry without changing its stable account ID. Deleting the profile deletes its combined grant/credential record.

The service, keys, application identity and AppData paths remain stable and outside the app bundle, so normal in-place updates retain credentials. Access still depends on the same OS account, retained application data and accessible keychain; uninstall/data deletion, changed signing identity and keychain recovery are not guaranteed. Automated restart/update tests recreate managers with retained injected storage; no real keychain or OS-update migration was exercised.

## Complete OAuth grants and renewable sessions

The C++-only `acceptOAuthGrant(response, clientId, deviceToken)` entry point accepts a genuine successful OAuth response from a trusted token-endpoint integration. It validates the grant, UserProfile and Accounts before storing a versioned JSON envelope in the existing QtKeychain `RobinHoodAuthX` slot. The envelope preserves the complete original response, original client/device binding, verified principal, server-issued expiry and retained refresh/scope context. The device token is supplied from the original authorization context when the server omits it; it is not fabricated as a server response. Access/refresh secrets are **not** written to QSettings, plaintext JSON metadata, QML properties or logs. Legacy bare-bearer and version-1 envelope entries remain compatible. Version-2 renewal preserves native credentials in the secure envelope without including them in refresh requests.

`initializeSession(index)` (also used by `startSession(index)`) reads only the selected saved profile's secure record, even if its access token expired. A refreshable primary bundle immediately issues a typed form POST to the exact configured OAuth token endpoint with `grant_type=refresh_token`, its saved `refresh_token`, original `client_id`, `device_token` and scope. The request uses verified TLS, manual redirects, no ambient cookies/cache/Authorization header, a 16-second absolute deadline and a 1 MiB response cap. Generic dispatch rejects refresh credentials and refresh grants after merging defaults with caller input, regardless of route name; the legacy `Login` route accepts only its explicit password-grant schema. `send("TokenRefresh")` is also blocked. Successful renewal validates scope and stable account identity, stores any rotated refresh token, and uses the newly minted **access token only** in subsequent bearer headers. No password or MFA workflow is started during successful refresh. Rejected/revoked grants require sign-in again; local state is never treated as a server authorization decision.

While idle, the active profile is checked every 30 seconds and renewed when its access expiry is within 120 seconds. Other saved profiles are not automatically authenticated. Renewal does not change credentials during a trading lease or retry an ambiguous order POST. The picker exposes **Renew Session** for expired profiles with the non-secret `canRefresh` hint; the actual secure record and server response still determine whether renewal succeeds. **Reauthenticate** appears only for a selected profile that is already expired or expires within the next two hours (inclusive). Eligibility updates on selection, expiry changes and the 30-second clock tick; busy-state protection remains unchanged.

Credential reads and mutations acquire a separate nonblocking cross-process `.credentials.lock` reservation, held through renewal, asynchronous secure-store completion, rollback and metadata commit. Store callbacks co-own that reservation if their manager is destroyed. Legacy saves, browser/OAuth commits and deletion/slot reuse respect the same reservation. Persistent profile ownership, a monotonic credential revision/high-water mark, an exact-secret digest and renewal-pending state bind each attempt to the credential it read; successful rotation does not reset that discriminator. Before a refresh request, owner-private atomic metadata records the attempt. After rotation, a securely saved new grant is retained if non-secret metadata publication fails rather than restoring a potentially revoked old refresh token. Uncertain/failed reconciliation blocks activation until safe recovery or reauthentication. These cooperating-writer checks are not an atomic transaction across the provider, QtKeychain and disk.

Neither a 30-day refresh lifetime nor a 24-hour access lifetime is hardcoded. Access expiry comes from `expires_in`; the provider controls refresh-token validity, revocation and additional authentication requirements. Reading a JSON file or decoding a token alone does not prove trading permission. Native sign-in now supplies initial complete grants; browser secondary cookies and legacy access-only records still cannot be transformed into refreshable primary grants.

## Account information and local holdings

Brokerage-account cards appear only on **Account overview**, after starting a session. **Your sessions** shows saved login profiles and session actions, not cached brokerage accounts or cache-availability placeholders; selecting a profile does not read its cached accounts for presentation. Each overview card has a small lowercase-**i** image button with keyboard focus, accessible account identity and a tooltip. It opens read-only information showing stock/instrument labels, exact fractional share strings, last successful update time and **Stored snapshot · Not live data**. Switching/deleting profiles discards the private dialog state.

Successful Start Session verifies Accounts, then requests positions separately using each verified `account_number`, follows bounded same-origin pagination, and optionally resolves instrument symbols. A snapshot is published only after a complete validated positions response. Failed/unauthorized/truncated refresh preserves the last successful shares; explicit successful empty holdings clears the old snapshot. Missing symbols use an explicit instrument-ID label rather than an invented ticker. Limits are 100 pages, 10,000 positions and 200 instrument lookups per account. Secondary-token holdings access remains provisional, not proven by offline tests. Switch account remains available during an optional holdings refresh and cancels the pending read before returning to the picker. The existing Accounts envelope contract treats a successful results array without next as complete/non-paginated; a nonempty next is rejected rather than publishing a partial account list. An authoritative complete empty account list removes cached account rows.

Sanitized per-profile/per-brokerage-account snapshots are stored in each session's `accounts_cache` field in AppData `robinhood/sessions.json`, using file locking, atomic writes and owner-only read/write permissions. They survive restart and are removed with the saved profile. This financial snapshot is **not encrypted**; it is readable by the same OS user. Snapshot persistence remains unchanged, but the saved-profile picker does not expose its contents. Tokens remain separate in QtKeychain; no raw authenticated responses or token fields are stored in the holdings cache. The trading controller never uses cached holdings to size sell orders; it obtains a fresh, account-filtered position and subtracts supported reservation fields using exact decimal strings.

## Manual stock orders

The account overview includes Publics-style comma-separated ticker entry, **Buy** (one share of every ticker per active brokerage account) and **Sell All** (each account's freshly verified sellable shares). The scope is every eligible active brokerage account among the displayed accounts in the **active login only**, including its standard brokerage and IRA accounts. Fresh authoritative state excludes inactive/closed accounts; missing or newly active identities stop the batch rather than silently widening scope. Other saved login profiles are never authenticated or included automatically. Symbols are uppercased, deduplicated in first-entered order and validated without stripping punctuation into a different security. Limits are 20 distinct tickers, 20 accounts and 100 account/ticker rows.

`RobinTrades` exposes only presentation state and submission/cancellation methods. `RHTradeController` uses a private C++ session lease from `RHSessionManager` through `makeRHTradingDependencies()`; tokens remain outside QML. The lease freezes the active identity until completion/cancellation, including the final cooldown. Read-only/expired sessions disable orders with a reason. Native reauthentication can supply a complete primary grant after verification; retained secondary-only records remain read-only. Local decoding or successful identity reads alone never promote secondary credentials.

Processing is **ticker outer, account inner**, in displayed account order: AAPL/account 1, AAPL/account 2, AAPL/account 3, then the next ticker. The first order follows account/quote preflight without an artificial initial cooldown. Every account/ticker result schedules a freshly sampled asynchronous **2000–3000 ms** cooldown, including the final result; the batch remains busy until that final cooldown finishes. There are no parallel order submissions or GUI-thread sleeps. Each stock request has an absolute 16-second deadline in addition to its inactivity timeout, so slow progress cannot hold the lease indefinitely. Cancel/Stop remaining prevents further work; it does **not** cancel accepted broker orders. An interrupted POST can still execute and is reported as unknown, not safely cancelled.

Fresh account scope, exact instrument identity/tradability and account association are checked before dispatch. Sell sizes use fresh per-account positions, exact decimal subtraction of known reservations, and reject unsafe/zero quantities rather than creating a short. Regular-hours day buys follow the requested frozen-quote policy: fetch each distinct ticker's instrument and quote once before any buy POST; use `last_trade_price >= 1` for an actual market buy and `< 1` for a fixed limit at the captured `ask_price + 0.01`. Exactly $1 uses market. All eligible accounts reuse that ticker's validated snapshot/order plan; another batch fetches another snapshot. Invalid or incomplete preflight aborts before any buy. Decimal-string arithmetic preserves the requested maximum without floating-point errors or silently increasing it through rounding. This intentionally replaces the pinned upstream's unconditional 5% buy collar: neither new buy path sends `preset_percent_limit`. Sells remain market orders with fresh sellable sizing. Extended-hours trading is not enabled. Each submission has a fresh UUID `ref_id`. This unofficial contract is source-verified, not a live-provider compatibility guarantee.

Like Publics, **Debug builds preview by default; live order dispatch is enabled in Release builds** (or by the existing explicit `RELEASE_BUILD` opt-in for a custom configuration). The Debug live-path test seam works only with an explicitly configured loopback transport, never a real brokerage origin. Even in Release, the dedicated stock-order transport rejects secondary auth, unapproved origins/paths, redirects and arbitrary payload fields. Existing generic/read-only dispatch is not widened to arbitrary authenticated POSTs.

The results screen shows every eligible active-account/ticker row, exact requested quantity, order/reference ID when available and a reason for failures. **Submitted** means accepted/queued, not filled; **Filled** requires an explicit filled response. Timeout, malformed or ambiguous submission responses are **Unknown** and stop remaining orders without retry. Check Robinhood before manually retrying an unknown order. A missing display-only symbol does not invalidate a receipt when its instrument URL and all required order-correlation fields match; a present symbol must still match. Incomplete acknowledgements with a safe broker order ID get one bounded read-only `GET /orders/{id}/` check using the same primary session. Only a strongly correlated, recognized broker state can permit continuation; no order POST is retried. The client-generated **Reference ID** is not substituted for the broker's order ID. Reconciliation ownership checks snapshot identity on the GUI thread and read/validate at most 64 MiB of metadata on a worker. Checks are single-flight, refreshed no sooner than 250 ms apart, and guarded by session/batch generations. The verification deadline remains active while metadata is pending, even after the GET completes; cancellation and expiry remain responsive. Receipt acceptance requires an ownership probe initiated after the GET finishes; a previously started periodic probe cannot authorize promotion even if its successful result arrives later. Oversized, invalid, stale or timed-out verification stays Unknown without another order POST. Existing admission/dispatch ownership checks retain their prior behavior. Safe diagnostic reason codes and HTTP/network status identify remaining uncertainty without exposing raw responses or credentials.

Results do not fabricate fills or mutate cached holdings as though a queued order had executed; start a new session to refresh the stored snapshot. An interrupted historical batch is not automatically resumed or replayed: inspect the already-submitted account before placing a new batch. Development tests use synthetic tokens/stores and loopback HTTP only, with no real sign-ins, keychain entries or trades.

Ticker entry uppercases ASCII letters immediately during user edits while preserving cursor position, separators, whitespace and non-ASCII characters. Invalid characters still reach the strict ticker validator unchanged rather than silently becoming another symbol.

A penny-stock limit is a maximum purchase price, not a fill guarantee. Frozen quotes can age as the serial batch proceeds; they are intentionally not fetched again between accounts. Market execution prices are not fixed by the initial snapshot. The broker may reject unsupported order types, unavailable securities or price precision. No automatic repricing or retry is performed.

## Persistence contract

A dedicated commit gate prevents cancellation/replacement from interrupting credential reconciliation or model publication. Failed replacement persistence restores the previous credential before publishing an actionable failure. If secure-store rollback itself fails, activation is quarantined until successful reauthentication **for the current manager lifetime only**; this is not a durable crash-recovery journal or an atomic transaction spanning QtKeychain and JSON. The cross-process reservation serializes cooperating credential writers; cross-store crash consistency remains limited.

`SecureCredentialLocker` and its QtKeychain-protected AES-256-GCM `profiles.dat` format remain only for legacy data compatibility/cleanup, not new native persistence. Native staging reuses its encrypted-RAM PendingCredentials helper, not its legacy password file. Existing passwords are not silently erased or reused. QtKeychain uses the OS credential facility, not guaranteed AES Secure Enclave storage. Reinstall/update recovery requires retained AppData, stable signing/application identity and accessible keychain entries. Qt/framework/browser/network copies prevent a promise of complete RAM erasure. See `locker-security.md` for historical format details.

## Secondary-token transport limitation

The secondary cookie is not the official web app's primary API access token. `sendAuthenticated()` provisionally maps it to `Authorization: Bearer <value>` for scoped UserProfile/Accounts verification and account-filtered Positions/validated instrument GETs. This mapping is unverified against a live account and can be rejected: HTTP 401/403 yields an explicit error and **no saved session**. No verified Phoenix route/secondary transport contract was available, so none is fabricated or enabled. Authenticated requests enforce host/path restrictions, manual redirects and cookie loading/saving disabled; loopback requires an explicit test-only flag. No token goes into URLs or logs.

## Legacy browser modules and isolation

Historical browser regression coverage uses matching Qt WebEngineQuick (desktop) or Qt WebView (Android scaffolding). Production native QML registers neither WebEngineView nor QtWebView. Missing browser modules do not disable the native form. Desktop builds and tests require a matching WebEngine module; see the stock-order planning progress for the actual configurations and verification results. Qt6.12 Android packaging requires a full JDK21 or newer; a JRE alone is insufficient. Configure the JDK location in Qt Creator as well as JAVA_HOME for terminal builds. Installing QtWebView does not enable the security-gated Android backend.

Desktop profiles are memory-only, reject certificate errors and external top-level navigation, and allow browser subresources/frames needed by the provider. Android QtWebView uses an application-wide native cookie jar rather than a per-login profile: only the named secondary cookie is reset, and account switching/site logout remains controlled by the official website. CookieManager does not return expiry/attributes; the native browser enforces the `__Host-` contract. The app does not globally erase cookies or website storage belonging to other applets.

A real browser does **not** guarantee embedded-login acceptance, CAPTCHA completion or a push notification. No gr_token is forged or CAPTCHA bypassed. Offline tests use synthetic cookies, injected keys/stores, mocked QML browser content and loopback HTTP; no real credentials/keychain entries/trades are accessed. Native capture, Android compilation and live provider/API acceptance are separate verification layers.
